Workshop เก็บ Requirement ต้องถามอะไรบ้าง?

หลายครั้ง Workshop เก็บ Requirement ใช้เวลานานมาก
แต่จบประชุมแล้วทีมยังตอบไม่ได้ว่า:

ปัญหาจริงคืออะไร?
ใครคือผู้ใช้งานจริง?
ระบบต้องทำอะไร?
ข้อมูลอะไรต้องใช้?
ใครต้องอนุมัติ?
แบบไหนถึงเรียกว่าเสร็จ?
และมี constraint อะไรที่ต้องระวัง?

สุดท้าย Requirement ที่ได้เลยยังไม่พร้อมส่งต่อให้ Dev / QA
เพราะคุยกันเยอะ แต่ยังสรุปไม่ชัด

Workshop ที่ดีไม่ใช่แค่การเรียกทุกคนมาคุย
แต่ต้องช่วยให้ทีมเข้าใจปัญหา ผู้ใช้ process และสิ่งที่ต้องทำต่อให้ตรงกัน

5 เรื่องที่ควรถามใน Requirement Workshop

1. ปัญหาคืออะไร?

ก่อนถามว่า “อยากได้ feature อะไร”
ควรถามก่อนว่า “กำลังแก้ปัญหาอะไร”

คำถามที่ควรถาม:

ตอนนี้มี pain point อะไร?
ใครได้รับผลกระทบ?
ปัญหานี้เกิดบ่อยแค่ไหน?
ถ้าไม่แก้ จะเกิดอะไรขึ้น?
เป้าหมายของการแก้ปัญหานี้คืออะไร?

เพราะ Requirement ที่ดีควรเริ่มจากปัญหา
ไม่ใช่เริ่มจาก feature

2. ใครคือผู้ใช้?

คำว่า user อาจไม่ได้มีแค่คนเดียว

บางระบบมีทั้ง:

คนใช้งานจริง
คนอนุมัติ
คนตรวจสอบ
คนดู report
คนดูแลระบบ
ผู้บริหารที่ใช้ข้อมูลตัดสินใจ

คำถามที่ควรถาม:

ใครคือผู้ใช้งานหลัก?
ใครเป็นคนเริ่ม process?
ใครต้อง approve?
ใครได้รับ notification?
ใครเป็นคนตัดสินใจสุดท้าย?
มี role หรือ permission ต่างกันไหม?

ถ้าไม่แยก user ให้ชัด
Flow จะเริ่มมั่ว และสิทธิ์การใช้งานจะหลุดง่าย

3. ต้องการให้ระบบทำอะไร?

ส่วนนี้คือการแปลง business need ให้กลายเป็นสิ่งที่ทีมทำงานต่อได้

คำถามที่ควรถาม:

ระบบต้องช่วยเรื่องไหน?
ขั้นตอนการทำงานปัจจุบันเป็นอย่างไร?
To-be process ควรเป็นอย่างไร?
ต้องกรอกข้อมูลอะไร?
ต้องใช้ข้อมูลจากระบบอื่นไหม?
Input คืออะไร?
Output คืออะไร?
มี notification หรือ report อะไรที่ต้องใช้ไหม?

จุดสำคัญคืออย่าฟังแค่คำว่า “อยากได้ระบบ”
แต่ต้องเข้าใจ process จริงว่าทีมทำงานอย่างไร

4. แบบไหนถึงเรียกว่าเสร็จ?

ถ้าไม่คุยเรื่อง Done ตั้งแต่ต้น
ตอน UAT มักจะมีประโยคคลาสสิกว่า:

“อันนี้ไม่ใช่แบบที่คิด”

คำถามที่ควรถาม:

ผลลัพธ์ที่คาดหวังคืออะไร?
ต้อง test อะไรบ้าง?
case ไหนถือว่าผ่าน?
case ไหนถือว่าไม่ผ่าน?
ใครเป็นคน confirm?
ต้องมี acceptance criteria อะไร?
หลังทำเสร็จ ผู้ใช้ต้องเห็นอะไร?

ส่วนนี้คือจุดเริ่มต้นของ Acceptance Criteria

5. มีข้อจำกัดอะไรบ้าง?

Requirement ที่ดีต้องรู้ทั้งสิ่งที่อยากได้ และสิ่งที่ทำไม่ได้หรือทำยาก

คำถามที่ควรถาม:

มี deadline ไหม?
มี budget หรือ resource constraint ไหม?
ติด policy อะไรหรือเปล่า?
มีข้อจำกัดด้าน data ไหม?
ต้องเชื่อมกับระบบเดิมไหม?
มี dependency กับทีมอื่นไหม?
มีเรื่อง security หรือ compliance ที่ต้องระวังไหม?
มีอะไรที่ out of scope ชัดเจนไหม?

ถ้าไม่คุย constraint ตั้งแต่ต้น
งานจะดูเหมือนง่ายในห้องประชุม
แต่จะไปติดจริงตอนออกแบบหรือพัฒนา

ลำดับการคุยใน Workshop แบบง่าย ๆ

เริ่มจากปัญหา
ระบุผู้ใช้และ stakeholder
วาด process หรือ flow
คุย requirement และเงื่อนไข
สรุปสิ่งที่ต้องทำ owner และ next step

ระวัง Workshop แบบนี้

คุยแต่ solution แต่ยังไม่เข้าใจปัญหา
มีแต่คนพูด แต่ไม่มีคนสรุป
ถามกว้างเกินไปจนได้คำตอบลอย ๆ
จบประชุมแต่ไม่มี action item
ไม่มี owner ของแต่ละเรื่อง
ไม่สรุป decision หลังจบ workshop

Checklist ก่อนจบ Workshop

ก่อนปิดประชุม ลองเช็กว่า:

ปัญหาและเป้าหมายชัดเจนไหม?
รู้แล้วว่าใครคือ user และ stakeholder ใช่ไหม?
เห็น process as-is / to-be ตรงกันไหม?
Requirement หลักถูกสรุปแล้วหรือยัง?
Constraint ถูกบันทึกครบไหม?
มี owner และ next step ชัดเจนไหม?

Workshop ที่ดีไม่ใช่คุยเยอะ
แต่คือคุยให้ชัด และจบด้วยสิ่งที่ทีมเอาไปทำต่อได้จริง
