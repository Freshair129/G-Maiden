BA ควรคุยกับ Dev ยังไง?

หลายครั้งงานไม่ได้ช้าเพราะ Dev ไม่เก่ง
และไม่ได้พังเพราะ BA เขียนเอกสารไม่ดีเสมอไป

แต่พังเพราะ BA กับ Dev “คุยกันไม่เข้าใจ”

BA คิดว่าอธิบายครบแล้ว
Dev คิดว่ายังไม่รู้ว่าต้องทำอะไร
User คิดว่าระบบควรเป็นอีกแบบ
สุดท้ายงานวนกลับมาแก้ซ้ำ เพราะทุกคนเข้าใจภาพไม่เหมือนกัน

จริง ๆ แล้ว BA ไม่จำเป็นต้องเขียนโค้ดเป็น
แต่ BA ควรคุยกับ Dev ให้ชัดพอว่า:

ทำไมต้องทำเรื่องนี้
User ต้องการอะไร
Flow เป็นยังไง
Scope อยู่ตรงไหน
Business Rule คืออะไร
และแบบไหนถึงเรียกว่าเสร็จ

ทำไม BA ต้องคุยกับ Dev ให้ดี?

เพราะ Dev ไม่ได้ต้องการแค่ Requirement ที่เขียนยาว
แต่ต้องการความเข้าใจที่ชัดพอจะออกแบบและพัฒนางานต่อได้

ถ้า BA คุยกับ Dev ดี จะช่วยให้:

ลดความเข้าใจผิดของ Requirement
ลดงานแก้และ Rework
ทำให้ Dev เห็นภาพ Business Context
หา Solution ที่เหมาะกว่าได้
Estimate งานได้แม่นขึ้น
ลดความเสี่ยงก่อนเริ่มพัฒนา

BA ควรคุยกับ Dev ตอนไหนบ้าง?

1. ตั้งแต่ต้น ก่อนสรุป Requirement

อย่ารอให้ Requirement เสร็จ 100% แล้วค่อยส่งให้ Dev
บางครั้ง Dev ช่วยเห็นข้อจำกัดหรือความเป็นไปได้ตั้งแต่ต้นได้

เช่น:

ระบบเดิมรองรับไหม?
ข้อมูลมีจริงไหม?
Integration ต้องใช้เวลาไหม?
Flow นี้ทำยากเกินไปหรือเปล่า?
มีวิธีที่ง่ายกว่าไหม?

2. ระหว่างทำ Requirement

เมื่อมีข้อสงสัยหรือมี Change
ควรคุยกับ Dev เพื่อดูผลกระทบก่อน

เช่น:

ถ้าเพิ่ม Field นี้ กระทบ Database ไหม?
ถ้าเปลี่ยน Flow นี้ กระทบ API หรือระบบอื่นไหม?
ถ้าต้องทำ Report เพิ่ม ต้องใช้ข้อมูลจากไหน?
ถ้า User ขอแบบนี้ มีข้อจำกัดอะไรไหม?

3. ก่อนส่งงานเข้า Development

ก่อนส่งงานให้ Dev ควรเช็กว่า:

Requirement ชัดไหม?
Scope / Out of Scope ชัดไหม?
Flow หรือ Screen มีไหม?
Business Rule ครบไหม?
Acceptance Criteria พร้อมไหม?
มีตัวอย่างข้อมูลหรือ Test Scenario ไหม?
Dependency ถูกระบุแล้วไหม?

4. ก่อน UAT

BA ควร sync กับ Dev ว่า:

งานที่ทำตรงกับ Requirement ไหม?
มีข้อจำกัดอะไรที่ต้องแจ้ง User ไหม?
มี Known Issue หรือไม่?
ต้องเตรียมข้อมูลทดสอบอะไร?
Case ไหนควรให้ User ทดสอบเป็นพิเศษ?

5. หลังส่งงาน

หลังงานเสร็จ ควรคุยกันเพื่อเรียนรู้ว่า:

Requirement ส่วนไหนยังไม่ชัด?
Dev ต้องถามกลับตรงไหนบ่อย?
Flow หรือ AC พอไหม?
รอบหน้าควรเตรียมอะไรให้ดีขึ้น?

คุยยังไงให้ได้ประโยชน์?

1. เตรียมข้อมูลให้พร้อม

อย่าเริ่มด้วยคำว่า:

“ทำระบบนี้ให้หน่อย”

แต่ควรบอกว่า:

ปัญหาคืออะไร
ใครเป็น User
ต้องการผลลัพธ์อะไร
Process ปัจจุบันเป็นอย่างไร
Scope อยู่ตรงไหน
Constraint คืออะไร

2. ใช้ภาษาที่เข้าใจกัน

BA ไม่ควรอธิบายแบบ Business ล้วน ๆ จน Dev จับไม่ได้ว่าจะทำอะไร
และไม่จำเป็นต้องพูด Technical ลึกเกินไปจนหลุดจากเป้าหมาย

วิธีที่ดีคือเชื่อม Business กับ System ให้ Dev เห็นภาพ

เช่น:

แทนที่จะพูดว่า
“User อยากได้ Report เพิ่ม”

ให้พูดว่า
“User ต้องการ Report ยอดขายรายวัน โดยกรองตามสาขาได้ และ Export Excel ได้ เพื่อใช้สรุปยอดขายให้หัวหน้าทีมทุกเช้า”

3. โฟกัสเป้าหมาย ไม่ใช่สั่งวิธีทำ

BA ควรบอกว่า “ต้องการผลลัพธ์อะไร”
ไม่ใช่ล็อกวิธีทำทุกอย่างตั้งแต่ต้น

เพราะบางครั้ง Dev อาจมี Solution ที่ง่ายกว่า เร็วกว่า หรือเสี่ยงน้อยกว่า

ตัวอย่าง:

ไม่ควรพูดแค่ว่า
“เพิ่มปุ่มตรงนี้ แล้วให้ไปหน้านั้น”

ควรอธิบายว่า
“User ต้องการดูรายละเอียดก่อนยืนยัน เพื่อป้องกันการส่งข้อมูลผิด”

4. เปิดใจรับข้อเสนอแนะ

Dev อาจเห็นมุมที่ BA หรือ User ไม่เห็น เช่น:

ทำแบบนี้กระทบระบบเดิม
ข้อมูลนี้ไม่มีใน Database
API ยังไม่รองรับ
ต้องใช้เวลามากกว่าที่คิด
มีทางเลือกที่ทำง่ายกว่า

BA ที่ดีควรฟังและช่วยพา Dev กับ Business หาทางออกที่เหมาะสมร่วมกัน

5. ถามให้เคลียร์

ถ้าไม่เข้าใจ Technical term ให้ถาม
ถ้า Dev ไม่เข้าใจ Business flow ให้ BA อธิบายเพิ่ม

ไม่ต้องกลัวว่าจะดูไม่รู้
เพราะการถามให้ชัดตั้งแต่ต้น ดีกว่าเข้าใจผิดแล้วไปแก้ตอนท้าย

ประโยคที่ใช้ได้:

“ส่วนนี้กระทบระบบอื่นไหมครับ?”
“ถ้าทำแบบนี้ มีข้อจำกัดอะไรไหม?”
“มีทางเลือกที่ง่ายกว่านี้ไหม?”
“ถ้าเพิ่ม requirement นี้ จะกระทบ timeline แค่ไหน?”
“ช่วยอธิบายเป็น flow ง่าย ๆ ให้ทีมเข้าใจตรงกันได้ไหม?”

ตัวอย่างการคุยที่ไม่ค่อยดี

BA: “หน้าจอนี้ต้องมีปุ่ม แล้วกดแล้วต้องไปหน้านั้น แล้วต้องโชว์ข้อมูลทั้งหมดในตาราง”
Dev: “ข้อมูลไหนนะครับ?”
BA: “ก็ข้อมูลทั้งหมดอะครับ”

แบบนี้ Dev ยังไม่รู้ว่า:

ข้อมูลอะไร
มาจากไหน
กรองยังไง
ใครใช้
ใช้ไปเพื่ออะไร
ต้องเรียงลำดับหรือคำนวณอะไรไหม

ตัวอย่างการคุยที่ดีขึ้น

BA: “User ต้องการค้นหาข้อมูลลูกค้าและดูรายละเอียดการสั่งซื้อ เพื่อช่วยตอบคำถามลูกค้าได้เร็วขึ้น”

Dev: “ต้องค้นหาจากอะไรได้บ้างครับ?”

BA: “ค้นหาจากชื่อ เบอร์โทร และเลข order ได้ครับ ผลลัพธ์ควรแสดงสถานะ order, วันที่สั่งซื้อ และยอดรวม”

Dev: “ถ้าข้อมูลเยอะ อาจต้องทำ pagination นะครับ”

BA: “โอเคครับ งั้นขอใส่เป็น requirement เพิ่มว่าแสดงผลแบบแบ่งหน้า และรองรับการค้นหาด้วย keyword ครับ”

แบบนี้คุยแล้วได้ทั้งเป้าหมาย ขอบเขต และข้อจำกัดทางเทคนิค

Checklist ก่อนคุยกับ Dev

ก่อนส่งงานหรือคุยกับ Dev ลองเช็กว่า:

รู้เป้าหมายของ Feature นี้ชัดแล้วหรือยัง?
User คือใคร และ Flow หลักคืออะไร?
Scope / Out of Scope ชัดไหม?
มี Business Rule สำคัญครบไหม?
มีตัวอย่างข้อมูลหรือ Scenario ไหม?
มี Acceptance Criteria หรือ Test Condition ไหม?
มี Dependency หรือระบบที่เกี่ยวข้องไหม?
มีอะไรที่ยังไม่แน่ใจและต้องถาม Dev ไหม?
ถ้าไม่ทำงานนี้ จะกระทบอะไร?

สรุปง่าย ๆ

BA ไม่จำเป็นต้องเขียนโค้ดเป็น
แต่ต้องคุยให้ Dev เข้าใจว่า:

ปัญหาคืออะไร
ใครใช้งาน
ต้องการผลลัพธ์อะไร
ขอบเขตอยู่ตรงไหน
และแบบไหนถึงเรียกว่าเสร็จ

จำไว้ว่า:

BA ที่ดีไม่ใช่คนสั่ง Dev
แต่คือคนช่วยให้ Dev เข้าใจปัญหา และสร้าง Solution ได้ถูกทาง
