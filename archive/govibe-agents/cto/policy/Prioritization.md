Prioritization ทำยังไง? งานไหนควรทำก่อน?

หลายทีมไม่ได้ติดปัญหาว่า “ไม่มีงานทำ”
แต่ติดปัญหาว่า “งานเยอะเกินไป แล้วไม่รู้ว่าอะไรควรทำก่อน”

Backlog เต็มไปหมด
Stakeholder ขอหลายเรื่อง
User อยากได้หลายอย่าง
Dev อยากแก้ technical debt
Management อยากเห็น quick win
และทุกคนมักคิดว่างานของตัวเองสำคัญที่สุด

ถ้าไม่มีวิธีจัด Priority ที่ชัดเจน
ทีมจะเริ่มทำงานแบบ reactive คือใครเสียงดัง ใครเร่งกว่า งานนั้นขึ้นมาก่อน

สุดท้ายทีมอาจยุ่งมาก
แต่ไม่ได้ส่งมอบ value ที่สำคัญจริง ๆ

Prioritization คืออะไร?

Prioritization คือการตัดสินใจว่า
งานไหนควรทำก่อน งานไหนรอได้ และงานไหนอาจไม่ต้องทำตอนนี้

ไม่ใช่แค่การเรียงลำดับงานตามความรู้สึก
แต่ควรดูจาก value, impact, urgency, effort, risk และ dependency

พูดง่าย ๆ:

Prioritization = เลือกทำสิ่งที่สำคัญที่สุดก่อน ไม่ใช่ทำทุกอย่างพร้อมกัน

5 ปัจจัยที่ควรใช้จัด Priority

1. Value

งานนี้สร้าง value แค่ไหน?

คำถามที่ควรถาม:

ทำแล้ว user ได้ประโยชน์อะไร?
ช่วยแก้ pain point สำคัญไหม?
ช่วยเพิ่มรายได้ ลด cost หรือลด manual work ไหม?
ทำแล้ว business ได้ผลลัพธ์อะไร?

ถ้า value ไม่ชัด งานนั้นอาจยังไม่ควรถูกดันขึ้นมาเป็น priority สูง

2. Urgency

งานนี้ต้องทำตอนนี้ไหม?

บางงานสำคัญ แต่ยังไม่รีบ
บางงานไม่ได้ใหญ่ แต่ต้องทำก่อนเพราะมี deadline หรือ regulatory impact

คำถามที่ควรถาม:

ถ้าไม่ทำตอนนี้ จะเกิดอะไรขึ้น?
มี deadline จริงไหม?
มี commitment กับ stakeholder แล้วหรือยัง?
งานนี้ block งานอื่นไหม?

อย่าปล่อยให้ทุกอย่างกลายเป็น “ด่วน”
เพราะถ้าทุกอย่างด่วน แปลว่าไม่มีอะไรด่วนจริง

3. Impact

งานนี้กระทบคนหรือระบบมากแค่ไหน?

คำถามที่ควรถาม:

กระทบ user กี่กลุ่ม?
กระทบ process สำคัญไหม?
กระทบ operation หรือ service ไหม?
ถ้าทำสำเร็จ จะเปลี่ยนผลลัพธ์ได้มากแค่ไหน?

Impact สูง ไม่ได้แปลว่าต้องทำทันทีเสมอ
แต่ควรถูกมองอย่างจริงจังใน decision

4. Effort

งานนี้ใช้ effort แค่ไหน?

คำถามที่ควรถาม:

ใช้เวลาเท่าไหร่?
ต้องใช้ทีมไหนบ้าง?
Technical complexity สูงไหม?
ต้องทำ integration หรือ migration ไหม?
ต้องใช้ UAT หรือ rollout ซับซ้อนไหม?

งาน value สูงแต่ effort สูง อาจต้องวางแผนดี
งาน value สูง effort ต่ำ อาจเป็น quick win ที่ควรหยิบมาก่อน

5. Risk / Dependency

งานนี้มีความเสี่ยงหรือ dependency อะไรไหม?

คำถามที่ควรถาม:

ต้องรอข้อมูลจากใครไหม?
ต้องรอระบบอื่นไหม?
มี security / compliance risk ไหม?
ถ้าเลื่อนงานนี้ จะกระทบงานอื่นหรือไม่?
มี decision ที่ยังไม่ชัดไหม?

บางงาน priority สูง แต่ dependency ยังไม่พร้อม
ทีมอาจต้องทำ discovery หรือ clear blocker ก่อน

Framework ที่ใช้ช่วยจัด Priority ได้

MoSCoW

แบ่งงานเป็น 4 กลุ่ม:

Must Have
ต้องมี ไม่ทำไม่ได้

Should Have
ควรมี แต่ถ้าไม่ทันยังพอเลื่อนได้

Could Have
มีแล้วดี แต่ยังไม่จำเป็น

Won’t Have for Now
ยังไม่ทำในรอบนี้

MoSCoW เหมาะกับการคุย scope กับ stakeholder เพราะเข้าใจง่าย

RICE Scoring

ใช้คะแนนช่วยเปรียบเทียบงาน:

Reach = กระทบคนกี่คน
Impact = กระทบมากแค่ไหน
Confidence = มั่นใจในข้อมูลแค่ไหน
Effort = ใช้แรงเท่าไหร่

สูตรคิดแบบง่าย:

RICE = Reach × Impact × Confidence ÷ Effort

RICE เหมาะกับทีม Product ที่ต้องเปรียบเทียบ feature หลายตัว และอยากให้ decision มีเหตุผลมากขึ้น

Prioritization ที่ควรระวัง

เลือกจากคนที่เสียงดังที่สุด
เลือกจากคนที่ตำแหน่งสูงที่สุดเสมอ
เลือกแต่ quick win จนไม่แก้ปัญหาใหญ่
เลือกแต่งานใหญ่จนไม่มีอะไรส่งมอบเร็ว
ไม่ดู dependency
ไม่ทบทวน priority เมื่อ context เปลี่ยน
ไม่สื่อสารเหตุผลว่าทำไมบางงานต้องรอ

Checklist ก่อนจัด Priority

ลองถามทีมว่า:

งานนี้สร้าง value อะไร?
ถ้าไม่ทำตอนนี้ จะเสียอะไร?
กระทบ user หรือ business มากแค่ไหน?
ใช้ effort เท่าไหร่?
มี risk หรือ dependency อะไร?
มีข้อมูลพอให้ตัดสินใจไหม?
ถ้าทำงานนี้ก่อน ต้องเลื่อนงานอะไรออก?
ใครควรเป็นคนตัดสินใจ priority สุดท้าย?

สรุปง่าย ๆ

Prioritization ที่ดีไม่ใช่การทำให้ทุกคนพอใจ
แต่คือการช่วยให้ทีมเลือกสิ่งที่ควรทำก่อน ด้วยเหตุผลที่ชัดเจน

จำไว้ว่า:

Priority ไม่ใช่ “ใครเสียงดังสุด”
แต่คือ “อะไรสร้าง value มากที่สุดในเวลานี้”
