CASE 3: Requirement ไม่ชัด ควรถามอะไรต่อ?
ในโปรเจกต์จริง เราเจอ Requirement แบบนี้บ่อยมาก:
“ขอ Report เพิ่ม”
“เอาแบบใช้ง่าย ๆ”
“ขอระบบอนุมัติ”
“อยากให้ดูภาพรวมได้”
“ทำให้เหมือนระบบเดิม”
“ขอให้ค้นหาได้”
“ขอให้แจ้งเตือนด้วย”
ประโยคพวกนี้ฟังดูเหมือนเข้าใจ
แต่พอส่งต่อให้ Dev, QA หรือ Vendor ทำจริง
มักจะเริ่มมีคำถามตามมาเต็มไปหมด
Report อะไร?
ใช้ง่ายคือแบบไหน?
ใครอนุมัติ?
อนุมัติกี่ขั้น?
ภาพรวมของ KPI ไหน?
ค้นหาจาก Field ไหน?
แจ้งเตือนใคร?
แจ้งเตือนช่องทางไหน?
ระบบเดิมส่วนไหนที่ต้องเหมือน?
ปัญหาไม่ใช่ User พูดไม่เก่งเสมอไป
แต่หลายครั้งคือทีมยังถามไม่ครบ
ดังนั้นถ้า Requirement ยังไม่ชัด
อย่าเพิ่งรีบรับปาก
และอย่าเพิ่งรีบส่งต่อให้ Dev
ให้ถามต่อให้ครบก่อน
1. ใครใช้?
คำถามแรกที่ควรถามคือ
ใครคือ User หรือ Role ที่ใช้งานจริง?
เพราะคำว่า “User” กว้างมาก
และแต่ละ Role อาจมี Flow, Permission และความต้องการไม่เหมือนกัน
คำถามที่ควรถาม:
ใครเป็นคนใช้งานจริง?
ใครเป็นคนกรอกข้อมูล?
ใครเป็นคนอนุมัติ?
ใครเป็นคนดู Report?
แต่ละ Role เห็นข้อมูลเหมือนกันไหม?
มีสิทธิ์การใช้งานต่างกันไหม?
ตัวอย่าง:
จากเดิม:
“ขอระบบอนุมัติ”
ถามต่อให้ชัด:
ใครเป็นคนส่งคำขอ?
ใครเป็นคนอนุมัติ?
อนุมัติกี่ Level?
ถ้า Reject ต้องเกิดอะไรขึ้น?
2. ต้องการทำอะไร?
Requirement ต้องบอก Action หรือ Flow ให้ชัด
คำถามที่ควรถาม:
User ต้องการทำ Action อะไร?
Create, View, Update, Delete, Approve, Export หรือ Search?
ต้องทำจากหน้าจอไหน?
ต้องทำทีละรายการหรือหลายรายการ?
Flow เริ่มจากตรงไหนและจบตรงไหน?
มี Exception หรือ Error Case ไหม?
ตัวอย่าง:
จากเดิม:
“ขอให้ค้นหาได้”
ถามต่อให้ชัด:
ค้นหาจากอะไรได้บ้าง?
ค้นหาแบบบางส่วนได้ไหม?
ถ้าไม่เจอข้อมูลต้องแสดงอะไร?
ผลลัพธ์ต้องเรียงยังไง?
3. ทำไปเพื่ออะไร?
Requirement ที่ดีควรเชื่อมกับเหตุผลหรือ Business Value
เพราะถ้าไม่รู้ว่าทำไปเพื่ออะไร
ทีมอาจสร้าง Feature ได้ แต่ไม่ได้แก้ปัญหาจริง
คำถามที่ควรถาม:
แก้ปัญหาอะไร?
User เจอ Pain Point อะไร?
ทำแล้วลด Manual Work ไหม?
ทำแล้วลด Error ไหม?
ทำแล้วช่วยให้ตัดสินใจเร็วขึ้นไหม?
ถ้าไม่ทำตอนนี้ จะกระทบอะไร?
ตัวอย่าง:
จากเดิม:
“ขอ Report เพิ่ม”
ถามต่อให้ชัด:
Report นี้ใช้ตัดสินใจอะไร?
ใครเป็นคนใช้?
ต้องดูข้อมูลรายวัน รายเดือน หรือ Real-time?
ต้อง Export เพื่อนำไปทำงานต่อไหม?
4. มีเงื่อนไขอะไร?
Requirement มักพังเพราะ Business Rule ไม่ครบ
คำถามที่ควรถาม:
มี Status อะไรบ้าง?
มี Permission หรือ Role อะไรบ้าง?
มี Field ไหนบังคับกรอกไหม?
ข้อมูลมาจากระบบไหน?
มีเงื่อนไขการคำนวณไหม?
มี Approval Rule ไหม?
มี SLA หรือ Deadline ไหม?
ถ้าข้อมูลผิดหรือไม่ครบ ระบบต้องทำอะไร?
มีการเชื่อมต่อกับระบบอื่นไหม?
ตัวอย่าง:
จากเดิม:
“ต้องแจ้งเตือนเมื่อมีงานใหม่”
ถามต่อให้ชัด:
แจ้งเตือนใคร?
แจ้งผ่าน Email, Line, Push หรือ In-app?
แจ้งเมื่อ Status ไหน?
แจ้งซ้ำไหมถ้าไม่มีคนตอบ?
ต้องเก็บ Log ไหม?
5. แบบไหนถึงเรียกว่า Done?
Requirement ที่ไม่ชัด มักไม่มี Acceptance Criteria
ถ้าไม่มี AC
Dev อาจทำตามความเข้าใจตัวเอง
QA Test ไม่ครบ
และ User อาจบอกตอน UAT ว่า “ไม่ใช่แบบที่คิด”
คำถามที่ควรถาม:
ผลลัพธ์ที่คาดหวังคืออะไร?
แบบไหนถือว่าผ่าน?
ต้องมี Positive Case อะไรบ้าง?
ต้องมี Negative Case อะไรบ้าง?
ถ้า Error ต้องแสดงอะไร?
ใครเป็นคน Confirm ว่าผ่าน?
ต้องมีหลักฐานอะไรตอน UAT?
ตัวอย่าง AC:
User สามารถค้นหาด้วยชื่อหรือเลขอ้างอิงได้
ระบบต้องแสดงผลลัพธ์ที่ตรงกับ Keyword
ถ้าไม่พบข้อมูล ระบบต้องแสดงข้อความ “ไม่พบข้อมูล”
ผลการค้นหาต้องแสดงภายใน 3 วินาที
ประโยคที่ใช้ถามได้จริง
“ผู้ใช้งานหลักของ Flow นี้คือใครครับ?”
“ขั้นตอนหลักที่อยากให้ทำได้คืออะไรครับ?”
“ปัญหาที่อยากแก้จริง ๆ คืออะไรครับ?”
“มีเงื่อนไขหรือข้อยกเว้นอะไรที่ต้องรองรับไหมครับ?”
“ถ้าทำเสร็จแล้ว แบบไหนถึงเรียกว่าโอเคครับ?”
“ขอช่วยยกตัวอย่าง Case จริงที่ User เจอได้ไหมครับ?”
“มีตัวอย่าง Report / หน้าจอ / ไฟล์ที่ใช้อยู่ตอนนี้ไหมครับ?”
“ถ้า Requirement นี้ยังไม่ทำในรอบนี้ จะกระทบอะไรบ้างครับ?”
สิ่งที่ไม่ควรทำ
อย่าตอบว่า “ได้ครับ” ทันที ถ้ายังไม่เข้าใจ Requirement
อย่าส่งให้ Dev ทั้งที่ยังไม่รู้ User, Flow, Rule และ AC
อย่าคิดว่า “เดี๋ยวค่อยไปเคลียร์ตอน UAT”
อย่าปล่อยให้คำว่า “ใช้ง่าย ๆ” กลายเป็น Requirement หลัก
อย่าให้ทีมตีความกันเองจากประโยคกว้าง ๆ
สรุปง่าย ๆ
Requirement ไม่ชัด
ไม่ได้แปลว่า User ผิดเสมอไป
แต่อาจแปลว่า
ทีมยังถามไม่ครบ
จำง่าย ๆ:
**ถามให้ครบ**
**เช็ก Flow / Rule**
**สรุปให้ชัด**
**แล้วค่อยส่งต่อ**
Requirement ที่ดีต้องทำให้ทีมตอบได้ว่า:
ใครใช้
ต้องการทำอะไร
ทำไปเพื่ออะไร
มีเงื่อนไขอะไร
และแบบไหนถึงเรียกว่า Done
