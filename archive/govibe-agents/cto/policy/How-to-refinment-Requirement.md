 Requirement ให้ดีขึ้น

หลายทีมเจอ Requirement แบบนี้บ่อยมาก:

“ระบบต้องใช้งานง่าย”
“ขอ Report เพิ่ม”
“ต้องแจ้งเตือน”
“Dashboard ต้องดูภาพรวมได้”
“ระบบต้องเร็ว”
“User ต้องค้นหาข้อมูลได้”

ประโยคพวกนี้ไม่ได้ผิดทั้งหมด
แต่ปัญหาคือ “ยังไม่ชัดพอ” ให้ทีมเอาไปทำงานต่อ

Dev ยังไม่รู้ว่าต้อง Build อะไร
QA ยังไม่รู้ว่าจะ Test ยังไง
User ยังไม่รู้ว่าแบบไหนเรียกว่า Done
PM / PO ยังไม่รู้ว่า Scope จบตรงไหน

ดังนั้นการแก้ Requirement ให้ดีขึ้น ไม่ใช่แค่เขียนให้ยาวขึ้น
แต่ต้องเขียนให้ “ชัดขึ้น วัดผลได้ และส่งต่อได้จริง”

หลักคิดง่าย ๆ: ใช้ 5 คำถามนี้
1. ใครใช้?

ก่อนเขียน Requirement ต้องรู้ก่อนว่า User หรือ Role คือใคร

คำถามที่ควรถาม:

ใครเป็นคนใช้งานจริง?
ใครเป็นคนอนุมัติ?
ใครเป็นคนดูข้อมูล?
แต่ละ Role มีสิทธิ์เหมือนกันไหม?

ตัวอย่างไม่ชัด:

“ระบบต้องอนุมัติได้”

แก้ให้ดีขึ้น:

“Manager สามารถอนุมัติหรือปฏิเสธคำขอของพนักงานในทีมได้”

2. ต้องการทำอะไร?

Requirement ต้องบอก Action ให้ชัด ไม่ใช่เขียนกว้าง ๆ

คำถามที่ควรถาม:

User ต้องการทำ action อะไร?
ต้อง Create, View, Update, Delete, Approve, Export หรือ Search?
ต้องทำจากหน้าจอไหน?
ต้องทำทีละรายการหรือหลายรายการ?

ตัวอย่างไม่ชัด:

“User ต้องค้นหาข้อมูลได้”

แก้ให้ดีขึ้น:

“User สามารถค้นหาคำขอด้วยเลขอ้างอิง ชื่อผู้ขอ หรือสถานะของคำขอได้”

3. ทำไปเพื่ออะไร?

Requirement ที่ดีควรเชื่อมกับเป้าหมายหรือ Value

คำถามที่ควรถาม:

แก้ pain point อะไร?
ลด manual work ไหม?
ช่วยให้ตัดสินใจเร็วขึ้นไหม?
ช่วยลด error หรือ delay ไหม?
Business ได้ประโยชน์อะไร?

ตัวอย่างไม่ชัด:

“ขอ Dashboard ดูภาพรวม”

แก้ให้ดีขึ้น:

“ผู้จัดการต้องการดูจำนวนงานที่รอดำเนินการ งานที่เสร็จแล้ว และงานที่เกิน SLA เพื่อใช้ติดตามงานค้างประจำวัน”

4. มีเงื่อนไขอะไร?

Requirement ที่ดีต้องมี Business Rule หรือเงื่อนไขสำคัญ

คำถามที่ควรถาม:

ต้องมี Field อะไรบ้าง?
ข้อมูลมาจากไหน?
มี Permission หรือ Role อะไร?
มี Status อะไร?
มี Approval กี่ขั้น?
ถ้า Error ต้องเกิดอะไรขึ้น?
มี Integration กับระบบอื่นไหม?

ตัวอย่างไม่ชัด:

“ต้องแจ้งเตือนเมื่อมีงานใหม่”

แก้ให้ดีขึ้น:

“ระบบต้องส่ง Email แจ้งเตือนไปยัง Approver เมื่อมีคำขอใหม่ และต้องแสดง Notification ในระบบให้ User เห็นสถานะล่าสุด”

5. แบบไหนถึงเรียกว่า Done?

สุดท้ายต้องมี Acceptance Criteria เพื่อให้ทีมรู้ว่า “ผ่าน” คืออะไร

ตัวอย่างไม่ชัด:

“ระบบต้องเร็ว”

แก้ให้ดีขึ้น:

“ระบบต้องแสดงผลการค้นหาภายใน 3 วินาที เมื่อมีข้อมูลไม่เกิน 10,000 records”

หรือเขียนเป็น AC:

Given User อยู่ที่หน้าค้นหา
When User กรอก keyword และกด Search
Then ระบบต้องแสดงผลลัพธ์ภายใน 3 วินาที
สูตรแก้ Requirement แบบง่าย

จากประโยคกว้าง ๆ ให้แปลงเป็น:

As a [User / Role]
I want to [Action]
So that [Benefit]

แล้วเติม:

Field / Data

ตัวอย่าง Before / After

Before:
“ขอ Report เพิ่ม”

After:
“User สามารถ Export Report รายการคำขอรายเดือนเป็น Excel ได้ โดยเลือกช่วงวันที่ สถานะ และทีมผู้รับผิดชอบได้”

Before:
“ระบบต้องอนุมัติได้”

After:
“Manager สามารถอนุมัติหรือปฏิเสธคำขอของพนักงานในทีมได้ โดยต้องระบุเหตุผลเมื่อปฏิเสธ และระบบต้องบันทึกวันเวลาในการตัดสินใจ”

Before:
“Dashboard ต้องดูภาพรวมได้”

After:
“Dashboard ต้องแสดงจำนวนงานทั้งหมด งานที่รอดำเนินการ งานที่เสร็จแล้ว และงานที่เกิน SLA แยกตามทีมผู้รับผิดชอบ”
