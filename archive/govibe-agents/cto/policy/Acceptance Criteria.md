กลับยังต้องถามต่อว่า…

อันนี้ต้องทำถึงแค่ไหน?
แบบไหนเรียกว่าผ่าน?
ถ้าข้อมูลไม่ครบต้องเกิดอะไรขึ้น?
ถ้ากด Submit แล้วต้องแสดงอะไร?
ใครเป็นคนยืนยันว่า Done?

นี่คือเหตุผลที่เราต้องมี Acceptance Criteria หรือ AC

Acceptance Criteria คืออะไร?

AC คือเงื่อนไขที่บอกว่า
งานนี้ต้องเป็นแบบไหน ถึงจะเรียกว่า “เสร็จ” หรือ “ผ่าน”

ถ้า User Story บอกว่า
“ผู้ใช้ต้องการทำอะไร”

Acceptance Criteria จะบอกว่า
“เราจะรู้ได้อย่างไรว่าทำถูกแล้ว”

จำง่าย ๆ:

User Story = สิ่งที่ต้องการทำ
Acceptance Criteria = แบบไหนถึงเรียกว่าเสร็จ

โครงสร้างที่ใช้ได้ง่าย: Given / When / Then

Given = สถานะเริ่มต้นคืออะไร
When = ผู้ใช้ทำอะไร
Then = ผลลัพธ์ที่ต้องเกิดขึ้นคืออะไร

ตัวอย่าง:

Given ผู้ใช้กรอกข้อมูลครบ
When ผู้ใช้กดปุ่ม Submit
Then ระบบต้องส่งคำขอ และแสดงสถานะเป็น Pending Approval

ประโยคนี้ดีเพราะทีมเข้าใจตรงกันว่า:

เริ่มจากเงื่อนไขอะไร
ผู้ใช้ทำ action อะไร
ระบบต้องตอบสนองอย่างไร
QA ต้อง Test อะไร
Dev ต้อง Build ให้ได้ผลลัพธ์แบบไหน

ตัวอย่าง AC ที่ดี

User สามารถเลือกวันเริ่มต้นและวันสิ้นสุดได้
User สามารถเลือกประเภทคำขอได้
User ต้องกรอกข้อมูลที่จำเป็นให้ครบก่อน Submit
เมื่อกด Submit ระบบต้องสร้างคำขอใหม่
หลัง Submit สำเร็จ ระบบต้องแสดงข้อความยืนยัน
คำขอต้องแสดงสถานะเป็น Pending Approval
ถ้าข้อมูลไม่ครบ ระบบต้องแจ้งเตือนให้ User แก้ไข

AC ที่ควรระวัง

“ระบบต้องใช้งานง่าย”
ยังไม่ชัดว่า easy คืออะไร

“ต้องแจ้งเตือน”
ยังไม่บอกว่าแจ้งเตือนตอนไหน ช่องทางไหน ข้อความอะไร

“กดแล้วต้องเร็ว”
ยังไม่มีเกณฑ์วัดว่าเร็วคือกี่วินาที

“ข้อมูลต้องถูกต้อง”
ยังไม่บอกว่าตรวจสอบยังไง และผิดแล้วต้องทำอย่างไร

คำกว้าง ๆ แบบนี้ทำให้ทีมตีความไม่เหมือนกัน
Dev อาจทำตามที่ตัวเองเข้าใจ
QA อาจ Test ไม่ครบ
User อาจบอกว่า “ไม่ใช่แบบที่คิด”

ก่อนส่งงานให้ทีม ลองเช็ก AC ด้วยคำถามนี้

Test ได้ไหม?
ชัดพอไหม?
วัดผลได้ไหม?
มีเงื่อนไขสำคัญครบไหม?
Dev, QA, BA, PO เข้าใจตรงกันไหม?

AC ที่ดีไม่จำเป็นต้องยาว
แต่ต้องชัดพอให้ทีมทำงานต่อได้จริง
