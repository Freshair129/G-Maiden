Checklist ก่อนส่งงานให้ Dev

หลายทีมมีปัญหาว่า Dev ถามกลับเยอะ
Estimate ยาก
เริ่มทำแล้วต้องหยุด
หรือทำไปแล้วต้องแก้ใหม่

บางครั้งไม่ใช่เพราะ Dev ไม่เข้าใจงาน
แต่เพราะสิ่งที่ส่งให้ Dev “ยังไม่พร้อมพอให้เริ่มทำ”

เช่น:

Requirement ยังไม่ชัด
Flow ยังไม่ครบ
Acceptance Criteria ไม่มี
Business Rule ยังไม่เคลียร์
Scope ยังเปิดกว้าง
User ยังตอบไม่ตรงกัน
หรือไม่มีตัวอย่างข้อมูลให้ดู

ถ้าอยากลดการถามกลับ ลด Rework และช่วยให้ Dev ทำงานง่ายขึ้น
ก่อนส่งงานให้ Dev ควรเช็ก 7 เรื่องนี้

1. เป้าหมายของงานชัดไหม

ก่อนคุยว่า “ต้องทำอะไร”
ควรตอบให้ได้ก่อนว่า “ทำไปเพื่ออะไร”

คำถามที่ควรตอบได้:

งานนี้แก้ปัญหาอะไร?
ใครได้รับประโยชน์?
Business ต้องการผลลัพธ์อะไร?
ถ้าไม่ทำ จะเกิดผลกระทบอะไร?

ถ้าเป้าหมายไม่ชัด
Dev อาจทำได้ตามคำสั่ง แต่ Solution อาจไม่ตอบโจทย์จริง

2. User / Role ชัดไหม

ต้องรู้ว่าใครคือคนใช้งานจริง
และแต่ละ Role ทำอะไรได้บ้าง

คำถามที่ควรตอบได้:

ใครเป็น User หลัก?
มี Role อะไรบ้าง?
ใคร Create, View, Edit, Approve หรือ Export ได้?
แต่ละ Role เห็นข้อมูลเหมือนกันไหม?
มี Permission หรือ Access Control อะไรไหม?

ถ้า Role ไม่ชัด
Flow, Permission และ Test Case จะหลุดง่ายมาก

3. Flow ชัดไหม

Dev ต้องเข้าใจว่า User ทำงานอย่างไร ตั้งแต่ต้นจนจบ

ควรมีอย่างน้อย:

As-is Flow ถ้าจำเป็น
To-be Flow
Step การทำงานหลัก
Exception Case
Error Case
จุดที่ระบบต้องแจ้งเตือน
จุดที่ต้องเชื่อมกับระบบอื่น

ถ้า Flow ไม่ชัด
Dev จะต้องเดาว่าระบบควรพาผู้ใช้ไปทางไหนต่อ

4. Scope / Out of Scope ชัดไหม

ก่อนเริ่ม Dev ต้องรู้ว่าอะไรทำ และอะไรยังไม่ทำ

ควรตอบได้ว่า:

Feature ไหนอยู่ในรอบนี้?
Feature ไหนเลื่อนไปรอบหน้า?
Report / Dashboard รวมอยู่ไหม?
Notification รวมอยู่ไหม?
Export รวมอยู่ไหม?
Mobile / Web ต้องรองรับแค่ไหน?
Integration อยู่ใน scope ไหม?

ถ้า Out of Scope ไม่ชัด
งานจะงอกง่าย และสุดท้ายกลายเป็น Scope Creep

5. Business Rule ครบไหม

Business Rule คือกติกาที่ระบบต้องทำตาม

ตัวอย่างเช่น:

Status มีอะไรบ้าง
การอนุมัติมีกี่ขั้น
ใครอนุมัติได้
ถ้า Reject ต้องใส่เหตุผลไหม
ถ้าข้อมูลไม่ครบ ระบบต้องทำอะไร
Deadline / SLA คิดยังไง
เงื่อนไขการคำนวณคืออะไร

Business Rule ที่ไม่ครบ
มักทำให้ Dev ทำผิดจากที่ Business คาดหวัง

6. Acceptance Criteria มีไหม

Acceptance Criteria หรือ AC ช่วยบอกว่าแบบไหนถึงเรียกว่า Done

ตัวอย่าง AC:

User สามารถกรอกข้อมูลที่จำเป็นได้ครบ
เมื่อกด Submit ระบบต้องสร้างคำขอใหม่
หลัง Submit สำเร็จ ระบบต้องแสดงข้อความยืนยัน
ถ้าข้อมูลไม่ครบ ระบบต้องแจ้งเตือนให้แก้ไข
รายการต้องแสดงสถานะ Pending Approval

ถ้าไม่มี AC
Dev ไม่รู้ขอบเขต Done
QA แตก Test Case ยาก
และ UAT มีโอกาสถกเถียงสูง

7. Data / Example พร้อมไหม

Dev ทำงานง่ายขึ้นมาก ถ้ามีตัวอย่างให้ดู

สิ่งที่ควรเตรียม:

ตัวอย่างข้อมูล Input
ตัวอย่าง Output
Mockup / Wireframe
ตัวอย่าง Report
ตัวอย่าง Error Message
ตัวอย่าง Email / Notification
Test Scenario สำคัญ
ข้อมูลที่ต้องใช้จากระบบอื่น

ตัวอย่างช่วยลดการตีความผิดได้เยอะมาก
โดยเฉพาะงานที่มี Rule หรือ Data ซับซ้อน

Checklist ก่อนส่งงานให้ Dev

ก่อนส่งงาน ลองเช็กว่า:

เป้าหมายชัดไหม?
User / Role ชัดไหม?
Flow ชัดไหม?
Scope / Out of Scope ชัดไหม?
Business Rule ครบไหม?
Acceptance Criteria มีไหม?
Data / Example พร้อมไหม?
มี Dependency หรือ Risk อะไรที่ Dev ต้องรู้ไหม?
Dev อ่านแล้ว Estimate ได้ไหม?
QA อ่านแล้วแตก Test Case ได้ไหม?
สรุปง่าย ๆ

การส่งงานให้ Dev ไม่ใช่แค่โยน Requirement ไปให้
แต่ต้องส่ง “ความเข้าใจที่พร้อมพอให้เริ่มทำงาน”

จำไว้ว่า:

Requirement ที่พร้อม = Dev ทำง่ายขึ้น QA Test ง่ายขึ้น และ UAT มั่วน้อยลง
