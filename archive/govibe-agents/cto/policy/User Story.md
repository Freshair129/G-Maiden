User Story เขียนยังไง?

หลายคนเข้าใจว่า User Story คือการเขียนตามสูตร:

As a [user], I want [goal], so that [benefit]

ซึ่งไม่ผิดครับ
แต่ถ้าเขียนแค่นี้แล้วจบ ยังไม่พอสำหรับการทำงานจริง

เพราะ User Story ที่ดีไม่ใช่แค่ “ประโยคสวย ๆ”
แต่ต้องช่วยให้ทีมเห็นภาพเดียวกันว่า:

ใครคือผู้ใช้งาน
เขาต้องการทำอะไร
เขาต้องการไปเพื่ออะไร
มี value อะไรที่ต้องส่งมอบ
และแบบไหนถึงเรียกว่าเสร็จจริง

ตัวอย่าง:

As an employee
I want to submit a leave request online
So that I can request time off without sending email

ประโยคนี้ช่วยให้ทีมเข้าใจ 3 เรื่อง:

1. User
ใครคือคนใช้งานจริง

2. Goal
เขาต้องการทำอะไร

3. Value
ทำไปเพื่อประโยชน์อะไร

แต่ในการทำงานจริง อย่าหยุดแค่ User Story
ต้องมีรายละเอียดต่อ เช่น:

ต้องกรอกวันที่ลาได้
ต้องเลือกประเภทการลาได้
ต้องใส่เหตุผลการลาได้
ต้องส่งคำขอไปหา approver ที่เกี่ยวข้อง
หลังส่งคำขอแล้วต้องเห็นสถานะ
ถ้าส่งสำเร็จต้องมีข้อความยืนยัน
ถ้าข้อมูลไม่ครบต้องแจ้งเตือน

ส่วนนี้ควรถูกเขียนต่อเป็น Acceptance Criteria

เช่น:

User สามารถเลือกวันเริ่มลาและวันสิ้นสุดได้
User สามารถเลือกประเภทการลาได้
User ต้องกรอกเหตุผลการลาได้
เมื่อกด Submit ระบบต้องส่งคำขอไปยังหัวหน้างาน
User ต้องเห็นข้อความยืนยันหลังส่งคำขอสำเร็จ
คำขอต้องแสดงสถานะเป็น “Pending Approval”

สรุปง่าย ๆ:

User Story ช่วยให้ทีมเข้าใจ “เป้าหมายและคุณค่า”
Acceptance Criteria ช่วยให้ทีมรู้ว่า “ต้องทำอะไรถึงเรียกว่า Done”

ถ้ามี User Story แต่ไม่มี Acceptance Criteria
Dev อาจตีความเอง
QA อาจ Test ไม่ครบ
และ User อาจบอกว่า “ไม่ใช่แบบที่คิด”

ก่อนเขียน User Story รอบหน้า
อย่าเขียนแค่ feature
ให้เขียนให้เห็น user, goal, value และเงื่อนไขที่ทำให้งาน Done จริง

เขียน User Story ยังไงให้ทีมเข้าใจตรงกัน?

User Story ที่ดี ไม่ใช่แค่เขียนให้ครบสูตร

As a [user]
I want [goal]
So that [benefit]

เพราะสูตรนี้ช่วยให้ทีมเข้าใจแค่ 3 เรื่องหลัก:

As a [user] = ใครคือผู้ใช้งาน
I want [goal] = ผู้ใช้งานต้องการทำอะไร
So that [benefit] = ทำไปเพื่อประโยชน์อะไร

แต่ในงานจริง ถ้าเขียนแค่นี้แล้วส่งต่อให้ Dev หรือ QA เลย
มีโอกาสสูงที่ทีมจะเข้าใจไม่ตรงกัน

ตัวอย่าง User Story:

As an employee
I want to submit a leave request online
So that I can request time off without sending email

ประโยคนี้ดีขึ้นกว่าการเขียนว่า “อยากได้ระบบลา”
เพราะทีมเริ่มเห็นแล้วว่า:

User คือ employee
Goal คือ submit a leave request online
Value คือ request time off without sending email

แต่ยังมีคำถามที่ทีมต้องรู้ต่อ เช่น:

ต้องเลือกวันที่ลาอย่างไร
ต้องเลือกประเภทการลาได้ไหม
ต้องใส่เหตุผลไหม
ต้องแนบไฟล์ได้หรือเปล่า
หลัง Submit แล้วคำขอไปหาใคร
User ต้องเห็นสถานะอะไร
ถ้ากรอกข้อมูลไม่ครบ ระบบต้องแจ้งอย่างไร
และแบบไหนถึงเรียกว่า Done

ส่วนนี้ต้องเขียนเป็น Acceptance Criteria

ตัวอย่าง Acceptance Criteria:

User สามารถเลือกวันเริ่มลาและวันสิ้นสุดลาได้
User สามารถเลือกประเภทการลาได้
User สามารถกรอกเหตุผลการลาได้
เมื่อกด Submit ระบบต้องส่งคำขอไปยังหัวหน้างาน
หลังส่งคำขอสำเร็จ User ต้องเห็นข้อความยืนยัน
คำขอต้องแสดงสถานะเป็น “Pending Approval”
ถ้าข้อมูลไม่ครบ ระบบต้องแจ้งเตือนให้ User แก้ไข

สรุปง่าย ๆ:

User Story = เป้าหมายของงาน
ช่วยตอบว่า WHY + WHAT

Acceptance Criteria = เงื่อนไขความสำเร็จ
ช่วยตอบว่า HOW / DONE คืออะไร

User Story ที่ควรระวัง:

“อยากได้ระบบขอลา”
ยังไม่บอกว่าใครใช้ ทำอะไร เพื่ออะไร

“ระบบต้องใช้งานง่าย”
ยังไม่ชัดว่า “ง่าย” คืออะไร

“ขออนุมัติได้”
ยังไม่บอกว่าอนุมัติอะไร มีกี่ขั้นตอน ใครอนุมัติ

“เพิ่ม Report”
ยังไม่บอกว่า Report อะไร ใช้ข้อมูลอะไร และเอาไปใช้ทำอะไร

ถ้า User Story ไม่ชัด
Dev ต้องเดา
QA Test ไม่ครบ
User ไม่ได้สิ่งที่คิดไว้
และทีมต้องกลับมาแก้งานซ้ำ

ดังนั้นก่อนส่ง User Story ให้ทีม
อย่าเช็กแค่ว่าเขียนครบสูตรหรือยัง
แต่ให้เช็กว่า “ทีมอ่านแล้วเข้าใจตรงกันหรือยัง”

 User Story ที่ดี

หลายทีมเขียน User Story ตามสูตรได้แล้ว:

As a [user]
I want [goal]
So that [benefit]

แต่ปัญหาคือ ถึงจะเขียนครบสูตรแล้ว
ทีมก็ยังอาจทำงานต่อไม่ได้ ถ้า Story ยังไม่ชัดพอ

เพราะ User Story ที่ดีไม่ใช่แค่ประโยคสวย ๆ
แต่ต้องช่วยให้ Dev, QA, BA, PO และ User เข้าใจตรงกันว่า:

ใครคือผู้ใช้งาน
เขาต้องการทำอะไร
ทำไปเพื่อประโยชน์อะไร
ขอบเขตอยู่ตรงไหน
และแบบไหนถึงเรียกว่า Done

ตัวอย่าง User Story ที่ยังไม่ดี

“User อยากจองห้องประชุมได้”

ประโยคนี้พอเข้าใจภาพรวม
แต่ยังไม่พอให้ทีมทำงานต่อได้จริง

ทีมยังต้องถามต่อว่า:

User คือใคร?
จองผ่านช่องทางไหน?
ต้องเลือกวันเวลาได้ไหม?
ต้องเห็นห้องที่ว่างไหม?
ต้องมีการยืนยันการจองไหม?
ต้องมีสถานะการจองไหม?
ถ้าห้องไม่ว่าง ระบบต้องทำอะไร?
แบบไหนถึงถือว่าจองสำเร็จ?

ถ้ายังตอบไม่ได้ User Story นี้ยังไม่พร้อมพอ

ตัวอย่าง User Story ที่ดีขึ้น

As an employee
I want to book a meeting room online
So that I can reserve a room without contacting admin

แบบนี้ดีขึ้น เพราะทีมเห็น 3 เรื่องหลัก:

User: Employee
Goal: Book a meeting room online
Benefit: Reserve a room without contacting admin

แต่ยังไม่จบแค่นี้

ถ้าจะให้ Dev และ QA ทำงานต่อได้จริง
ต้องมี Acceptance Criteria เพิ่ม

ตัวอย่าง Acceptance Criteria
User สามารถเลือกวันที่และเวลาในการจองได้
User สามารถเห็นรายการห้องที่ว่างตามวันและเวลาที่เลือกได้
User สามารถเลือกห้องประชุมและกดยืนยันการจองได้
หลังจองสำเร็จ ระบบต้องแสดงข้อความยืนยัน
รายการจองต้องแสดงสถานะเป็น Confirmed
ถ้าไม่มีห้องว่าง ระบบต้องแสดงข้อความแจ้งว่า “ไม่มีห้องว่างในช่วงเวลานี้”
User Story ที่ดีควรมีอะไร?
1. User ชัด

ต้องรู้ว่าใครเป็นคนใช้งานจริง

ไม่ควรเขียนกว้าง ๆ ว่า “User” ตลอด
ถ้ามีหลาย Role ควรแยกให้ชัด เช่น:

Employee
Manager
Admin
Approver
Customer
Operation Team

เพราะแต่ละ Role อาจมีสิทธิ์และ Flow ไม่เหมือนกัน

2. Goal ชัด

ต้องรู้ว่า User ต้องการทำ Action อะไร

เช่น:

Submit request
Book meeting room
Approve request
Export report
Search information
Track status

Goal ที่ดีควรเป็นสิ่งที่ User ต้องการทำจริง
ไม่ใช่แค่ชื่อ Feature กว้าง ๆ

3. Benefit ชัด

ต้องรู้ว่าทำไปเพื่ออะไร

ถ้าไม่มี Benefit
ทีมอาจทำ Feature ได้ แต่ไม่รู้ว่ามันแก้ปัญหาอะไร

ตัวอย่าง Benefit:

เพื่อลดการติดต่อ Admin
เพื่อติดตามสถานะได้เอง
เพื่อลด Manual Work
เพื่ออนุมัติคำขอได้เร็วขึ้น
เพื่อให้ทีมเห็นข้อมูลก่อนตัดสินใจ

Benefit ช่วยให้ทีมเข้าใจ Value ของงาน

4. Scope ชัด

User Story ที่ดีควรบอกขอบเขตให้พอเข้าใจ

เช่น:

ทำอะไรได้
ทำอะไรไม่ได้
Flow หลักคืออะไร
เงื่อนไขสำคัญคืออะไร
มีข้อจำกัดอะไร

ถ้า Scope ไม่ชัด
Story จะบานง่ายมาก

5. Acceptance Criteria ชัด

User Story ที่ดีควรมี AC เพื่อบอกว่าแบบไหนถึงเรียกว่า Done

ถ้าไม่มี AC
Dev อาจทำตามความเข้าใจของตัวเอง
QA อาจ Test ไม่ครบ
User อาจบอกว่า “ไม่ใช่แบบที่คิด”

ตัวอย่าง Before / After

Before:
“User อยากดู Report ได้”

After:
As a manager
I want to export a monthly request report
So that I can review team workload and pending items

Acceptance Criteria:

Manager สามารถเลือกช่วงวันที่ได้
Manager สามารถเลือกสถานะของคำขอได้
ระบบสามารถ Export เป็น Excel ได้
Report ต้องแสดงเลขคำขอ วันที่ สถานะ และผู้รับผิดชอบ

Before:
“User อยากติดตามสถานะได้”

After:
As an employee
I want to track my request status
So that I know whether my request is pending, approved, or rejected

Acceptance Criteria:

User สามารถดูรายการคำขอของตัวเองได้
แต่ละรายการต้องแสดงสถานะล่าสุด
ถ้าคำขอถูก Reject ต้องแสดงเหตุผล
User ต้องเห็นวันที่อัปเดตสถานะล่าสุด
Checklist ก่อนส่ง User Story ให้ทีม

ลองเช็กว่า:

User หรือ Role ชัดไหม?
Goal ชัดไหม?
Benefit ชัดไหม?
Story นี้แก้ปัญหาอะไร?
Scope ชัดพอไหม?
มี Business Rule สำคัญไหม?
มี Acceptance Criteria ไหม?
QA สามารถแตก Test Case ได้ไหม?
Dev เข้าใจพอที่จะ Estimate ได้ไหม?
User อ่านแล้วเข้าใจตรงกันไหม?
สรุปง่าย ๆ

User Story ที่ดีไม่ใช่แค่เขียนครบสูตร
แต่ต้องชัดพอให้ทีมเข้าใจตรงกันและทำงานต่อได้จริง

จำไว้ว่า:

User Story บอกว่าใครต้องการอะไร และทำไปเพื่ออะไร
Acceptance Criteria บอกว่าแบบไหนถึงเรียกว่า Done
