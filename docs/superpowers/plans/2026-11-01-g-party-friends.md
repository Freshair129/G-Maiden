# G-Party Friends Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add optional mutually accepted account Friends, private online presence, verified in-room GID links and consent-gated targeted invitations to G-Party.

**Architecture:** Private gstore relationship storage and an authenticated Edge broker coordinate with a configured HMAC-authenticated in-memory relay. Native Rust retains member credentials and admits friend tickets only while idle; the G-Party UI owns explicit consent and account/room epochs. Guest codes and local core continue independently.

**Tech Stack:** PostgreSQL/RLS/pgTAP, Supabase Edge/Deno TypeScript, Node built-in HTTP/crypto, existing Rust g-party/Tauri v2, React 18/TypeScript/Vitest.

**Spec:** `docs/superpowers/specs/2026-11-01-g-party-friends-design.md` — read it before this plan; its exact DTO/action/signature and security tables are normative.

## Global Constraints

- User authorized supervised multi-agent source implementation through merge; no repeated plan confirmation is needed. No hosted deployment, release, tag or version bump.
- No chat, voice, Steam import, searchable directory, public profile expansion, last-seen display, match activity tracking, automatic joining, deployment, release or version bump.
- Latest owner direction (2026-11-01): reuse existing design tokens, including typography, colors, spacing and radius; design a new layout freely without following the old page layout.
- Redesign G-Party around a dominant large minimap, room/member region and Friends rail. Preserve local capture/unknown states; no focus stealing or Overlay navigation changes.
- Friends and account failure never gate guest code create/join or local core.
- Ordinary social authorization requires a verified Google identity and live session at AAL1 or AAL2; existing IAM AAL2 and audit defaults remain unchanged for IAM callers.
- Friends 200/account, combined pending requests 50/account, blocks 500/account; presence heartbeat 20,000 ms, presence/link lease 60,000 ms, state polling 15,000 ms, invitation 300,000 ms, challenge/proof/ticket at most 60,000 ms.
- Broker request/response 8 KiB/256 KiB, decoded proof 2 KiB, broker timeout 5,000 ms, relay redeem timeout 3,000 ms; no redirects and one request per operation in flight.
- Rate limits, remaining capacities, cryptographic byte encodings, expiry boundaries and errors are copied from the spec, never independently invented by a lane.
- No account JWT/GID/UUID goes to the relay; no room member token or GMP1 secret enters social storage; account-room binding leases carry no gameplay payload.
- Persistent code belongs to this external-git-backed worktree. Use explicit file paths; preserve unrelated PR105 and other work. Only root commits/pushes/merges after integration/review and exact-head checks.

## Review Focus

1. A reciprocal request or two simultaneous acceptances must not accidentally establish a friendship or exceed either person's 200-friend cap (Task 1).
2. A delayed proof/renewal after unlink or switching accounts must not restore another account's room identity; native stale completion must not restore a departed membership (Tasks 2–4).
3. A block/remove committing while a ticket redeems must follow documented transaction ordering; a successful redemption followed by a full/rotated/closed room must show failed join (Tasks 1, 3, 4).
4. Hidden/revoked/expired presence must never remain online because a response was delayed or polling stopped, including multiple live provider sessions (Tasks 1, 4).
5. Arbitrary/redirected relay endpoints, noncanonical proof bytes, reused signed nonce, body oversize, unknown fields and missing configuration must fail closed while guest operation still works (Tasks 2, 3, 4).
