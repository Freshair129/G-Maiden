ตัวอย่าง Requirement ที่ไม่ดี

หลายทีมไม่ได้มีปัญหาเพราะ “ไม่มี Requirement”
แต่มีปัญหาเพราะ Requirement ที่ได้มา “ไม่ชัดพอให้ทีมทำงานต่อได้”

Requirement บางประโยคฟังดูเหมือนเข้าใจง่าย
แต่พอส่งต่อให้ Dev, QA หรือ User แล้ว ทุกคนตีความไม่เหมือนกัน

ตัวอย่าง Requirement ที่เจอบ่อย:

“ระบบต้องใช้งานง่าย”
“ขอ Report เพิ่ม”
“Dashboard ต้องดูภาพรวมได้”
“ต้องอนุมัติได้”
“ระบบต้องเร็ว”
“User ต้องค้นหาข้อมูลได้”
“ขอให้ Export Excel ได้”
“ต้องแจ้งเตือนเมื่อมีงานใหม่”

ประโยคพวกนี้ไม่ได้ผิดทั้งหมด
แต่มันยัง “ไม่พอ” สำหรับการทำงานจริง

เพราะทีมยังต้องถามต่อว่า:

ง่ายคืออะไร?
Report อะไร?
ดูภาพรวมของ KPI ไหน?
ใครอนุมัติ?
อนุมัติกี่ขั้น?
เร็วคือกี่วินาที?
ค้นหาจาก field ไหน?
Export ข้อมูลอะไร?
แจ้งเตือนช่องทางไหน?
แจ้งเตือนใคร?

ถ้าตอบคำถามพวกนี้ไม่ได้ Requirement ยังไม่พร้อมพอที่จะส่งต่อให้ทีมทำงาน

Requirement ที่ไม่ดีมักมี 5 อาการ
1. กว้างเกินไป

ตัวอย่าง:

“ระบบต้องใช้งานง่าย”

ปัญหาคือคำว่า “ง่าย” ของแต่ละคนไม่เหมือนกัน

User อาจหมายถึงกดน้อยลง
Dev อาจคิดว่า layout ไม่ซับซ้อน
Designer อาจคิดว่า UI ต้อง clean
QA อาจไม่รู้ว่าจะ test ยังไง

ควรเขียนให้ชัดขึ้น เช่น:

“User สามารถส่งคำขอได้ภายใน 3 ขั้นตอน และระบบต้องแสดงข้อความยืนยันหลัง Submit สำเร็จ”

2. ไม่มี User ชัดเจน

ตัวอย่าง:

“ระบบต้องอนุมัติได้”

คำถามคือ:

ใครเป็นคนส่งคำขอ?
ใครเป็นคนอนุมัติ?
มีกี่ level?
มี delegate ได้ไหม?
ถ้า reject แล้วเกิดอะไรขึ้น?
ถ้า approver ไม่ตอบ ต้องทำยังไง?

ถ้าไม่ระบุ user และ role ให้ชัด
Flow จะเริ่มมั่วทันที

ควรเขียนให้ชัดขึ้น เช่น:

“Manager สามารถอนุมัติหรือปฏิเสธคำขอของพนักงานในทีมได้ และระบบต้องบันทึกวันเวลาและเหตุผลของการตัดสินใจ”

3. ไม่มี Business Goal

ตัวอย่าง:

“ขอ Dashboard ดูภาพรวม”

คำถามคือ:

ดูภาพรวมเรื่องอะไร?
ใครเป็นคนดู?
ใช้ตัดสินใจอะไร?
ต้องดูทุกวันหรือทุกเดือน?
KPI ที่สำคัญคืออะไร?

ถ้าไม่มี Business Goal
ทีมอาจทำ Dashboard ที่สวย แต่ไม่ได้ช่วยตัดสินใจอะไรจริง

ควรเขียนให้ชัดขึ้น เช่น:

“ผู้จัดการต้องการดูจำนวนคำขอที่รอดำเนินการ แยกตามสถานะและทีมผู้รับผิดชอบ เพื่อใช้ติดตามงานค้างประจำวัน”

4. ไม่มี Acceptance Criteria

ตัวอย่าง:

“User ต้องค้นหาข้อมูลได้”

คำถามคือ:

ค้นหาจากอะไรได้บ้าง?
ค้นหาแบบ exact match หรือ partial match?
ถ้าไม่เจอข้อมูลต้องแสดงอะไร?
ผลลัพธ์ต้องเรียงยังไง?
ต้องใช้เวลาค้นหาไม่เกินกี่วินาที?

ถ้าไม่มี Acceptance Criteria
Dev อาจทำตามความเข้าใจของตัวเอง
QA อาจ test ไม่ครบ
User อาจบอกว่า “ไม่ใช่แบบที่คิด”

ควรเขียน AC เช่น:

User สามารถค้นหาด้วยชื่อหรือเลขอ้างอิงได้
ระบบต้องแสดงผลลัพธ์ที่ตรงกับ keyword
ถ้าไม่พบข้อมูล ระบบต้องแสดงข้อความ “ไม่พบข้อมูล”
ผลการค้นหาต้องแสดงภายใน 3 วินาที
5. Test ไม่ได้

ตัวอย่าง:

“ระบบต้องเร็ว”

คำว่าเร็ว test ยากมาก ถ้าไม่มีตัวเลข

เร็วสำหรับ user อาจหมายถึงทันที
เร็วสำหรับทีม technical อาจหมายถึงภายใน 5 วินาที
เร็วสำหรับ business อาจหมายถึงไม่ช้าจน user บ่น

ควรเขียนให้ test ได้ เช่น:

“ระบบต้องแสดงผลการค้นหาภายใน 3 วินาที เมื่อมีข้อมูลไม่เกิน 10,000 records”

Requirement ที่ดีควร test ได้
เพราะถ้า test ไม่ได้ ก็ยืนยันไม่ได้ว่าผ่านหรือไม่ผ่าน

ตัวอย่าง Before / After

Before:
“ขอ Report เพิ่ม”

After:
“User สามารถ Export Report รายการคำขอรายเดือนเป็น Excel ได้ โดยเลือกช่วงวันที่ สถานะ และทีมผู้รับผิดชอบได้”

Before:
“ระบบต้องแจ้งเตือน”

After:
“ระบบต้องส่ง Email แจ้งเตือนไปยัง Approver เมื่อมีคำขอใหม่ และต้องแสดง Notification ในระบบให้ User เห็นสถานะล่าสุด”

Before:
“Dashboard ต้องดูภาพรวมได้”

After:
“Dashboard ต้องแสดงจำนวนงานทั้งหมด งานที่รอดำเนินการ งานที่เสร็จแล้ว และงานที่เกิน SLA แยกตามทีมผู้รับผิดชอบ”

Checklist ก่อนส่ง Requirement ให้ทีม

ลองเช็กว่า Requirement ตอบคำถามเหล่านี้ได้ไหม:

ใครคือ User?
User ต้องการทำอะไร?
ทำไปเพื่อแก้ปัญหาอะไร?
Scope คืออะไร?
Out of Scope คืออะไร?
มี Business Rule อะไรบ้าง?
มี Acceptance Criteria ไหม?
QA สามารถ Test ได้ไหม?
Dev เข้าใจพอที่จะ Estimate ได้ไหม?
User อ่านแล้วเข้าใจตรงกันไหม?
สรุปง่าย ๆ

Requirement ที่ไม่ดีไม่ใช่แค่เขียนผิด
แต่คือ Requirement ที่ทำให้ทีมตีความกันเอง

จำไว้ว่า:

Requirement ที่ดีต้องไม่ใช่แค่อ่านแล้วดูเข้าใจ
แต่ต้องชัดพอให้ Dev ทำ QA Test และ User Confirm ได้
