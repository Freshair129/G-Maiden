CASE 1: User ขอเพิ่มงานกลางทาง ควรตอบยังไง?
ในโปรเจกต์จริง ประโยคนี้เจอบ่อยมาก:
“พี่ขอเพิ่มนิดเดียวเอง”
“เอาเข้า Release นี้ได้ไหม”
“เพิ่ม Report ให้อีกอัน”
“แก้จากของเดิมอีกนิด”
“ไม่น่ายากนะ แค่เพิ่ม Field เดียว”
ฟังดูเหมือนเรื่องเล็ก
แต่บางครั้ง “นิดเดียว” ของ User
อาจกลายเป็นงานใหญ่ของทีมได้
เพราะการเพิ่มงานกลางทาง อาจกระทบ:
Scope
Timeline
Resource
Quality
Test Case
UAT
และงานอื่นที่กำลังทำอยู่
ดังนั้นเวลามีคนขอเพิ่มงานกลางทาง
สิ่งที่ไม่ควรทำคือ
ตอบว่า “ได้ครับ” ทันที
ทั้งที่ยังไม่รู้ผลกระทบ
และสิ่งที่ไม่ควรทำอีกอย่างคือ
ปฏิเสธทันที
จนดูเหมือนไม่ช่วยแก้ปัญหาให้ Business
วิธีที่ดีกว่าคือ:
รับเรื่องไว้ก่อน แล้วเช็ก Impact ให้ครบ
1. เริ่มจากรับเรื่องแบบมืออาชีพ
ประโยคที่ใช้ได้:
“รับทราบครับ เดี๋ยวขอเช็กผลกระทบก่อนนะครับ”
“ขอเก็บรายละเอียดเพิ่มก่อนนะครับ จะได้ดูว่าเข้ารอบนี้ได้ไหม”
“ขอคุยกับทีมก่อน แล้วจะสรุปทางเลือกให้ครับ”
วิธีนี้ทำให้ User รู้ว่าเราไม่ได้ปัดตก
แต่เรายังไม่ commit จนกว่าจะรู้ Impact จริง
2. ถามให้ชัดว่าเพิ่มอะไร
อย่ารับคำว่า “เพิ่มนิดเดียว” แบบกว้าง ๆ
ต้องถามให้ชัดว่า:
เพิ่มอะไร?
เปลี่ยนตรงไหน?
เกี่ยวกับ Flow ไหน?
เกี่ยวกับหน้าจอไหน?
ต้องเพิ่ม Field, Report, Notification, Permission หรือ Business Rule?
สิ่งนี้เป็น Must-have หรือ Nice-to-have?
ถ้าไม่ถามให้ชัด
ทีมจะไม่รู้ว่าสิ่งที่เพิ่มคืออะไรจริง ๆ
3. ถามเหตุผลว่าทำไปเพื่ออะไร
งานที่เพิ่มควรมีเหตุผล ไม่ใช่เพิ่มเพราะ “น่าจะดี”
ถามต่อได้ว่า:
ต้องการแก้ปัญหาอะไร?
User ได้ประโยชน์อะไร?
ถ้าไม่ทำตอนนี้ จะเกิดผลกระทบอะไร?
จำเป็นต้องใช้ใน Release นี้จริงไหม?
มี workaround ชั่วคราวได้ไหม?
คำถามพวกนี้ช่วยแยกว่า
สิ่งที่ User ขอคือ “จำเป็นจริง” หรือ “อยากได้เพิ่ม”
4. เช็ก Impact กับทีม
ก่อนตอบรับ ต้องเช็กกับทีมก่อนว่า Impact คืออะไร
ควรดูอย่างน้อย:
Scope
งานนี้อยู่ใน Scope เดิมไหม หรือเป็น Scope ใหม่?
Timeline
ถ้ารับเพิ่ม จะกระทบ Milestone หรือ Go-live ไหม?
Effort / Resource
ต้องใช้ Dev, QA, BA, PO หรือ Vendor เพิ่มแค่ไหน?
Quality / Test
ต้องเพิ่ม Test Case หรือ Regression Test ไหม?
Dependency
กระทบระบบอื่น API Data หรือทีมอื่นไหม?
Cost
ถ้ามี Vendor จะมีค่าใช้จ่ายเพิ่มไหม?
5. สรุปทางเลือกให้ User / Stakeholder ตัดสินใจ
อย่าตอบแค่ “ได้” หรือ “ไม่ได้”
ให้สรุปเป็นทางเลือก เช่น:
Option A: รับเข้ารอบนี้
แต่ต้องเลื่อนงานบางรายการออก
Option B: ทำเป็น Change Request
ประเมิน Impact, Cost, Timeline แล้วขอ Approve ก่อน
Option C: ย้ายไป Phase ถัดไป
เพื่อลดความเสี่ยงของ Release ปัจจุบัน
Option D: ใช้ Workaround ชั่วคราว
แล้วค่อยพัฒนาเต็มในรอบถัดไป
วิธีนี้ทำให้การตัดสินใจอยู่บนข้อมูล ไม่ใช่อารมณ์
6. บันทึก Decision ให้ชัด
เมื่อมีการตัดสินใจแล้ว ต้องบันทึกไว้
ควรระบุว่า:
User ขออะไร
เหตุผลคืออะไร
Impact คืออะไร
Decision คืออะไร
ใคร Approve
จะทำในรอบไหน
กระทบอะไรบ้าง
เพราะถ้าไม่บันทึก
สุดท้ายอาจกลายเป็นงานงอกแบบไม่มีเจ้าของ
ประโยคที่ใช้ตอบได้จริง
“รับทราบครับ เดี๋ยวขอเช็กผลกระทบกับทีมก่อนนะครับ”
“ถ้ารับเพิ่มในรอบนี้ อาจกระทบ Timeline ของงานเดิม ขอประเมินก่อนนะครับ”
“ขอทราบเหตุผลและความจำเป็นของรายการนี้เพิ่มเติมนิดนึงครับ”
“รายการนี้เป็น Must-have สำหรับ Go-live รอบนี้ไหมครับ หรือสามารถย้ายไปรอบถัดไปได้?”
“ขอคุยกับทีมก่อน แล้วจะสรุปทางเลือกให้ตัดสินใจครับ”
“ถ้าต้องเพิ่มจริง ๆ อาจต้องเปิดเป็น Change Request เพื่อประเมิน Impact ให้ครบครับ”
สรุปง่าย ๆ
User ขอเพิ่มงานกลางทาง
ไม่ใช่เรื่องผิด
แต่สิ่งที่อันตรายคือ
การตอบรับโดยยังไม่รู้ผลกระทบ
จำไว้ว่า:
อย่ารับปากทันที
อย่าปฏิเสธทันที
แต่ให้เช็ก Impact แล้วเสนอทางเลือก
เพราะการรับเพิ่มงานที่ดี
ไม่ใช่การรับทุกอย่าง
แต่คือการรับอย่างมีข้อมูล
และทำให้ทุกฝ่ายเห็นผลกระทบจริง
