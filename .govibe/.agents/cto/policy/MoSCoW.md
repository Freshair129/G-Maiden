MoSCoW คืออะไร?

MoSCoW คือ framework สำหรับจัดลำดับความสำคัญของ requirement, feature หรือ backlog item

แบ่งงานออกเป็น 4 กลุ่ม:

M = Must Have
S = Should Have
C = Could Have
W = Won’t Have for Now

จุดประสงค์คือช่วยให้ทีมและ stakeholder คุยกันชัดขึ้นว่า
อะไรจำเป็นจริง
อะไรสำคัญแต่ยังเลื่อนได้
อะไรมีแล้วดี
และอะไรยังไม่ทำในรอบนี้

1. Must Have

Must Have คือสิ่งที่ “ต้องมี”
ถ้าไม่มีแล้วระบบใช้งานไม่ได้
Go-live ไม่ได้
หรือไม่สามารถส่งมอบเป้าหมายหลักได้

ตัวอย่าง:

Feature หลักที่จำเป็นต่อ process
Requirement ที่เกี่ยวกับกฎหมายหรือ compliance
Flow สำคัญที่ถ้าไม่มี user ทำงานต่อไม่ได้
Security หรือ permission ที่จำเป็น
ข้อมูลหลักที่ระบบต้องใช้

คำถามที่ควรถาม:

ถ้าไม่มีสิ่งนี้ ระบบยังใช้งานได้ไหม?
ถ้าไม่มีสิ่งนี้ ยัง Go-live ได้ไหม?
ถ้าไม่มีสิ่งนี้ จะผิดกฎ policy หรือ commitment ไหม?

ถ้าคำตอบคือ “ไม่ได้จริง ๆ”
ค่อยจัดเป็น Must Have

2. Should Have

Should Have คือสิ่งที่ “ควรมี”
สำคัญมาก
แต่ถ้าไม่ทันในรอบนี้ ยังพอมี workaround หรือเลื่อนไปได้

ตัวอย่าง:

Feature ที่ช่วยให้ process ดีขึ้น
Report ที่สำคัญแต่ยังใช้วิธี manual ชั่วคราวได้
Notification ที่ช่วยให้ user ทำงานง่ายขึ้น
Improvement ที่ช่วยลด manual work แต่ไม่ได้ block go-live

คำถามที่ควรถาม:

ถ้าไม่มีในรอบนี้ ยังใช้งานได้ไหม?
มี workaround ชั่วคราวไหม?
เลื่อนไป phase ถัดไปได้ไหม?
ถ้าเลื่อน จะกระทบมากแค่ไหน?

Should Have สำคัญ
แต่ยังไม่ critical เท่า Must Have

3. Could Have

Could Have คือสิ่งที่ “มีแล้วดี”
เป็น nice to have
ช่วยให้ระบบดูดีขึ้น ใช้ง่ายขึ้น หรือครบขึ้น
แต่ไม่กระทบการใช้งานหลักถ้ายังไม่มี

ตัวอย่าง:

UI enhancement
Filter เพิ่มเติม
Dashboard มุมเสริม
Option เพิ่มที่ไม่ได้จำเป็นกับ user ส่วนใหญ่
Automation ที่ช่วยประหยัดเวลาเล็กน้อย

คำถามที่ควรถาม:

ถ้าไม่มีสิ่งนี้ user ยังทำงานหลักได้ไหม?
สิ่งนี้ช่วยเพิ่ม value มากพอไหม?
ถ้ามีเวลาและ resource เหลือ ค่อยทำได้ไหม?

Could Have ไม่ได้แปลว่าไม่ดี
แค่ยังไม่ควรแย่ง capacity จากงานที่สำคัญกว่า

4. Won’t Have for Now

Won’t Have for Now คือสิ่งที่ “ยังไม่ทำในรอบนี้”

สำคัญมาก:
Won’t Have ไม่ได้แปลว่า “ไม่ทำตลอดไป”

แปลว่าใน scope, sprint, release หรือ phase นี้
ทีมตกลงกันว่าจะยังไม่ทำ

ตัวอย่าง:

Feature ที่ยังไม่มีข้อมูลพอ
Requirement ที่ value ยังไม่ชัด
งานที่ effort สูงแต่ impact ยังไม่คุ้ม
Idea ที่เก็บไว้พิจารณาใน phase ถัดไป
Feature ที่ยังไม่สอดคล้องกับเป้าหมายรอบนี้

คำถามที่ควรถาม:

ทำไมรอบนี้ยังไม่ควรทำ?
ควร revisit เมื่อไหร่?
มีเงื่อนไขอะไรที่ทำให้กลับมาพิจารณาใหม่?
ต้องสื่อสารกับ stakeholder ยังไง?

ใช้ MoSCoW ยังไงให้ไม่มั่ว

รวบรวม requirement หรือ backlog ทั้งหมด
คุยให้เข้าใจว่าแต่ละ item คืออะไร
แยก item เป็น Must / Should / Could / Won’t
เช็กกับ stakeholder ว่าเข้าใจตรงกันไหม
ทบทวนใหม่เมื่อ context เปลี่ยน

MoSCoW ไม่ใช่การให้คนใดคนหนึ่งตัดสินใจคนเดียว
แต่เป็นเครื่องมือช่วยให้ทุกฝ่ายคุยกันด้วยภาษาเดียวกัน

ข้อผิดพลาดที่เจอบ่อย

1. ทุกอย่างกลายเป็น Must Have

ถ้าทุกอย่างเป็น Must Have
แปลว่ายังไม่ได้ prioritize จริง

ทีมควรถามต่อว่า:

ถ้าไม่มีอันนี้ Go-live ไม่ได้จริงไหม?
หรือแค่ “อยากให้มี” ตั้งแต่รอบแรก?

2. ไม่สื่อสาร Won’t Have ให้ชัด

หลายทีมไม่กล้าบอกว่าอะไรจะยังไม่ทำ
สุดท้าย stakeholder คิดว่างานนั้นยังอยู่ใน scope

พอใกล้ Go-live ค่อยรู้ว่าไม่ได้ทำ
ก็กลายเป็น conflict ทันที

3. ใช้ MoSCoW ครั้งเดียวแล้วจบ

Priority เปลี่ยนได้
Context เปลี่ยนได้
Resource เปลี่ยนได้
ดังนั้น MoSCoW ควรถูก review เป็นระยะ

4. ใช้ความรู้สึกมากกว่าข้อมูล

MoSCoW จะดีขึ้นถ้าทีมมีข้อมูลประกอบ เช่น

User impact
Business value
Risk
Effort
Dependency
Deadline

Checklist ก่อนจัด MoSCoW

ลองถามทีมว่า:

Item นี้จำเป็นต่อ Go-live ไหม?
ถ้าไม่มี จะใช้งานหลักไม่ได้จริงไหม?
มี workaround ชั่วคราวไหม?
ทำแล้วสร้าง value แค่ไหน?
Effort สูงไหม?
มี dependency อะไรไหม?
รอบนี้จำเป็นต้องทำจริงไหม?
ถ้าไม่ทำรอบนี้ ต้องสื่อสารกับใครบ้าง?

สรุปง่าย ๆ

MoSCoW คือเครื่องมือช่วยคุยเรื่อง scope และ priority ให้ชัดขึ้น

Must Have = ต้องมี
Should Have = ควรมี
Could Have = มีแล้วดี
Won’t Have for Now = ยังไม่ทำในรอบนี้

จำไว้ว่า:

MoSCoW ไม่ได้ช่วยให้ทำทุกอย่าง
แต่ช่วยให้ทีมตกลงกันว่าอะไรควรทำก่อน
