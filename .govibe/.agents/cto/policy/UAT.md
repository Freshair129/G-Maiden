UAT คืออะไร? ทำไมต้องให้ User ทดสอบก่อน Go-live

หลายทีมเข้าใจว่า UAT คือรอบที่ให้ User มาลองกดระบบก่อน Go-live

เปิดระบบให้ลอง
ให้ User กด ๆ ดู
ถ้าไม่มี bug ใหญ่ก็ถือว่าผ่าน

แต่จริง ๆ แล้ว UAT ไม่ใช่แค่การลองใช้ระบบ
และไม่ใช่รอบที่เอาไว้ “หา bug อย่างเดียว”

UAT หรือ User Acceptance Testing
คือการทดสอบโดยผู้ใช้งานจริงหรือฝั่ง Business
เพื่อยืนยันว่าระบบที่ทำออกมาตอบโจทย์การทำงานจริง และพร้อมถูกยอมรับก่อนนำไปใช้งานจริง

พูดง่าย ๆ:

UAT = User ยืนยันว่าระบบใช้ทำงานจริงได้

UAT ต่างจาก Test อื่นยังไง?

Developer Testing
ทีม Dev เช็กว่า code หรือ function ทำงานตามที่พัฒนาไว้หรือไม่

System / Integration Testing
ทีม Test หรือ IT เช็กว่าระบบทำงานร่วมกันได้ไหม มี bug หรือ integration issue ไหม

UAT
User หรือ Business เช็กว่าระบบตอบโจทย์ process จริง และใช้งานได้ตามที่ตกลงกันไหม

ดังนั้น UAT ไม่ได้แทนที่การ test ของ Dev หรือ QA
แต่เป็นขั้นตอนที่ช่วยยืนยันจากมุมของผู้ใช้งานจริง

UAT ควรเช็กอะไรบ้าง?

1. Flow ใช้ได้จริงไหม

ระบบอาจทำงานถูกตาม technical spec
แต่ยังไม่ตรงกับวิธีทำงานจริงของ User

คำถามที่ควรถาม:

User ทำงานตาม process จริงได้ไหม?
ขั้นตอนขาดหรือเกินตรงไหนไหม?
Flow สะดุดตรงไหน?
ต้องใช้ข้อมูลอะไรระหว่างทาง?
มี role หรือ permission ที่ยังไม่ตรงไหม?

2. Requirement ตรงไหม

UAT คือจุดที่ต้องเช็กว่า
สิ่งที่ส่งมอบตรงกับ requirement ที่ตกลงกันหรือไม่

คำถามที่ควรถาม:

Feature ที่ตกลงไว้มีครบไหม?
Business rule ทำงานถูกไหม?
Field / screen / report ตรงตามที่ต้องการไหม?
ข้อมูลแสดงถูกต้องไหม?
มีอะไรที่ user คิดว่าขาด แต่ไม่ได้อยู่ใน scope ไหม?

3. Acceptance Criteria ผ่านไหม

ถ้า requirement มี AC ชัด
UAT จะง่ายขึ้นมาก

เพราะทีมจะรู้ว่า case ไหนต้องผ่าน
และอะไรคือเงื่อนไขความสำเร็จ

คำถามที่ควรถาม:

Test case ครอบคลุม AC แล้วหรือยัง?
เงื่อนไขสำคัญถูก test ครบไหม?
Case ที่ผ่านและไม่ผ่านถูกบันทึกไหม?
มีหลักฐานการ test ไหม?
ใครเป็นคน confirm ว่าผ่าน?

4. User ยอมรับได้ไหม

คำว่า acceptance ใน UAT สำคัญมาก

UAT ไม่ใช่แค่ระบบไม่มี error
แต่ User ต้องยอมรับว่าสามารถใช้ระบบนี้ทำงานจริงได้

คำถามที่ควรถาม:

User เข้าใจวิธีใช้งานไหม?
ระบบพร้อมใช้ในงานจริงไหม?
มี issue ไหนที่ต้องแก้ก่อน Go-live ไหม?
มี issue ไหนที่ยอมรับให้แก้หลัง Go-live ได้ไหม?
User หรือ Business sign-off ได้หรือยัง?

ขั้นตอน UAT แบบง่าย ๆ

1. เตรียม Scope ของ UAT
กำหนดว่ารอบนี้จะ test feature, flow หรือ module ไหนบ้าง

2. เตรียม Test Case
เขียน case ให้สอดคล้องกับ requirement และ acceptance criteria

3. เตรียม User / Tester
เลือกคนที่เข้าใจงานจริง และมีสิทธิ์ยืนยันผล

4. เตรียม Data และ Environment
ตรวจสอบว่าข้อมูล test และระบบพร้อมใช้งาน

5. Execute UAT
ให้ User ทดสอบตาม case และบันทึกผล

6. Log Issue
แยก issue เป็น bug, change request, gap หรือ training issue

7. Retest และ Sign-off
แก้ issue สำคัญ ทดสอบซ้ำ และให้ Business ยืนยันผล

สิ่งที่ควรระวังใน UAT

1. เริ่ม UAT โดยไม่มี Test Case

ถ้าไม่มี Test Case
User จะกดแบบสุ่ม ๆ และทีมจะไม่รู้ว่า test ครบหรือยัง

2. เอา Requirement ที่ไม่ชัดมา UAT

ถ้าตกลงกันไม่ชัดตั้งแต่ต้น
UAT จะกลายเป็นรอบถกเถียงว่า “อันนี้เคยคุยกันไหม”

3. ไม่แยก Bug กับ Change Request

บางอย่างคือระบบทำผิดจากที่ตกลง
บางอย่างคือ User ขอเพิ่มจาก scope เดิม

ถ้าไม่แยกให้ชัด
UAT จะกลายเป็นจุดเริ่มต้นของ Scope Creep

4. User ไม่ใช่คนใช้งานจริง

ถ้าคนทดสอบไม่เข้าใจ process จริง
อาจ test ผ่าน แต่พอ Go-live จริงเจอปัญหา

5. ไม่มี Sign-off

ถ้าไม่มีการยืนยันผลชัดเจน
หลัง Go-live อาจเกิดปัญหาว่า “ใครบอกว่าผ่าน?”

Checklist ก่อนเริ่ม UAT

ลองเช็กว่า:

Scope ของ UAT ชัดไหม?
Requirement และ AC พร้อมไหม?
Test Case ครอบคลุม flow สำคัญไหม?
User ที่มา test เป็นคนใช้งานจริงไหม?
Data และ Environment พร้อมไหม?
มีวิธี log issue ชัดเจนไหม?
แยก Bug / Change Request / Gap ได้ไหม?
มีเกณฑ์ Sign-off ชัดเจนไหม?

สรุปง่าย ๆ

UAT ที่ดีไม่ใช่รอบให้ User มากดเล่น
แต่คือรอบยืนยันว่า:

ระบบตรง Requirement ไหม
ใช้กับ Process จริงได้ไหม
User ยอมรับก่อน Go-live ได้ไหม

จำไว้ว่า:

UAT ไม่ใช่แค่ Test ระบบ
แต่คือ Test ว่าระบบพร้อมใช้กับงานจริงหรือยัง
